## 結果

2026-09-06、配布版 `a614553` および前回の列キャッシュ版 `473ef32` と比較。
生データの要約・ツールバージョン・ソースのSHA-256は `results.json` に記録。

| 項目 | 配布版 | 前回（列キャッシュ） | 今回（先読み並行化） |
| --- | ---: | ---: | ---: |
| 1世代の計算クロック数（MMIO START→BUSY解除） | 76,804 | 13,084 | **6,400** |
| 10 MHz換算の計算時間 | 7.6804 ms | 1.3084 ms | **0.6400 ms** |
| 配布版からの計算速度比 | 1 | 5.87 | **12.00** |
| 近傍の有効読み出し数／世代 | 24,000 | 5,400 | 5,400 |
| Yosys MAX10組合せセル | 1,015 | 1,208 | 1,223 |
| Yosys FF | 213 | 530 | 514 |
| Yosys DSPセル | 0 | 0 | 0 |
| グリッドRAM | 2,048 × 8 bit | 同左 | 同左 |
| 想定M9K数（グリッドのみ） | 2 | 2 | 2 |

前回から**2.04倍**の高速化です。組合せセルは15個増加、FFは16個減少し、
RAMとDSPを追加せずに計算時間を約半分にしました。

CPUクロック100 MHz、計算クロック10 MHzで測定しています。描画、CRC計算、
NES命令によるポーリング等を含む実機全体の速度ではありません。
CPU側の半周期を7 nsに変えた通信試験では6,400～6,401クロックでした。

## 設計

5×5の重みを `w = (3 - |dy|) + (2 - |dx|)` と分解します。
各列の人口合計・縦方向の重み付き合計・影響力・分類個数・中央セルを保持し、
セルを右に移すときは4列を再利用して新しい1列だけを読みます。
各行には最初の5列分25セルと、列をずらす31回分の5セルずつが必要なので、
`30 × (25 + 31 × 5) = 5,400` 読み出しです。
5列の集計はFFで保持し、M9Kを追加しません。

人口15～24の影響力は重みに依存しない `+2` なので、重みを掛ける係数を0にし、
縦方向の集計に一度だけ加えます。分類ごとの上限判定も元実装と揃えてあり、
CPUが通常範囲外の101～255を書き込んだ場合も扱えます。

RAM入力を状態・座標レジスタから直接駆動し、アドレス用の余分なレジスタを
なくしました。RAMの `q` は同期読み出しのまま、データタグを1クロック遅延します。
現在セルの演算と次セル用の列集計を独立して動かし、次の6クロックを繰り返します。

| 状態 | 現在セルの処理 | RAMポートA | 先読み列の集計 |
| --- | --- | --- | --- |
| SUM | 現在の5列から総和と自セルを保存 | 次の列のdy=−2を読む | — |
| AVG | 平均人口と都市数 | dy=−1を読む | dy=−2を取り込む |
| BIAS | バイアス計算 | dy=0を読む | dy=−1を取り込む |
| DELTA | 増減量を計算・制限 | dy=+1を読む | dy=0を取り込む |
| NEW_VALUE | 次世代値を保存 | dy=+2を読む | dy=+1を取り込む |
| WRITE | 結果を書き込み | 現在セルを別バンクへ書く | dy=+2を取り込み、列キャッシュをシフト |

SUMで現在セルの集計を保存するので、その後に列キャッシュをシフトしても演算を
壊しません。行末のx=31を計算する間は、次の行の最初の列（x=30）を先読みします。
次の行では残る4列を20クロックで補充します。最終セルでは先読みを停止します。

最終書き込みの次のクロックでDONEを通知します。各行の初回SUMまでに必ず
5列を更新し終えるため、列キャッシュのリセット回路は不要です。
START/DONEのトグル同期、ダブルバッファのバンク切り替え、MMIOの仕様を維持しています。

演算幅は人口の重み付き合計が15 bit（最大16,575）、影響力が符号付き9 bit
（−130～195）、分類個数が5 bitです。`/65` はシフト・減算・1回の余り補正、
`(force−20)/20` は境界比較に置き換え、Cと同じゼロ方向への丸めを維持します。
過密度の `/3` は符号なし8 bitに限定しています。

計算本体は `960 × 6 + (1 + 25 + 1) + 29 × (20 + 1) = 6,396` クロックです。
最初の行だけ初期設定・25セルの補充・読み出しの取り込み待ちが必要で、
それ以降は20セルの補充と1クロックの取り込み待ちです。開始同期と完了通知を含めて
6,400クロックになります。5,400読み出し＋960書き込み＝6,360回の有効RAMアクセスがあり、
同じ読み出し量と単一計算ポートを維持したまま削れる余白は小さくなっています。

## 再実行

C/C++コンパイラ、Python 3、Verilatorが必要です。追加検査にはIcarus Verilog、
リソース比較にはYosysを使います。Python外部パッケージは不要です。
[OSS CAD Suite](https://github.com/YosysHQ/oss-cad-suite-build) の `bin` をPATHに入れてください。
今回のツールは `/tmp/mics-fpga-tools/oss-cad-suite/bin` に配置しました。
リポジトリのルートから実行します。

```sh
export PATH=/tmp/mics-fpga-tools/oss-cad-suite/bin:$PATH

# 本検証：355配置、2,058世代。追加で算術と4値シミュレーションを実行
python3 Nescity_FPGA/eval/run.py --extra-checks

# 元回路の速度・動作を同じMMIOドライバで測る短い比較試験
python3 Nescity_FPGA/eval/run.py --baseline --steps 2 --smoke

# 前回の列キャッシュ版も同じドライバで比較
python3 Nescity_FPGA/eval/run.py --rtl-ref 473ef32 --steps 2 --smoke

# CPUクロックとの位相関係を変えた本検証
python3 Nescity_FPGA/eval/run.py --cpu-half 7

# アクセラレータ単体の合成比較とRAM/DSP・論理規模のガード
python3 Nescity_FPGA/eval/resources.py
```

短い動作確認には `run.py --steps 2 --smoke --extra-checks` を使えます。
生成物・ログは `.build/` に保存され、Git管理対象から除外されます。
回路やテストコードを変えたら `results.json` の過去測定とは区別してください。
スクリプトは失敗時に非ゼロで終了します。コンパイル詳細は `.build/*-build.log`、
合成詳細は `.build/*-synth.log` を参照してください。

## 正しさの検証範囲

`reference.c` は変更していないルートの `linux_city.c` を取り込みます。
Pythonから共有ライブラリ経由で初期配置・次世代を生成し、Verilatorで動かす
実RTLにCPUのMMIO経由で書き込み、各世代の全960セルを比較します。
RAMを内部から直接書き換える方式ではありません。

- 標準初期配置の1,280世代と、READMEのCRC全6点：
  `0000:37C2 / 0100:4963 / 0200:D350 / 0300:593A / 0400:EE30 / 0500:1FC3`。
- 0～255の全256種類の一様盤面を2世代ずつ。
- 分類境界の混在、通常値・全バイト値・海や山が多い固定乱数64配置を3世代ずつ。
- 四隅など7地点×4背景の単一セル配置を2世代ずつ、縦横の縞6配置を3世代ずつ。
- 正誤のアンロック列、長い書き込み、レジスタ署名、960セルの窓の範囲、
  BUSY中の読み出し・書き込み・制御命令、DONEの保持、世代カウンタ、
  ソフトリセット、計算中の非同期リセットと再アンロック。
  補充・各演算/先読みフェーズ・行境界・最終セル付近の18時点でリセットし、
  再初期化後に1世代を正常完了できることも確認。
- `/65` の到達可能な16,576入力と、影響力326入力を全数検査。
  全65,536組のself/avgに固定乱数の分類集計を与えてbias/deltaを元RTLと比較。
  全256 self×5 deltaの最終クランプも比較。
- Icarusの4値シミュレーションで初期化されていないRAM・列キャッシュを含めて
  2世代を実行し、両バンクの全セルにXや誤値が現れないことを確認。

Verilatorの `MULTIDRIVEN` 警告のみ、元からの独立2クロック真のデュアルポートRAMに
対して抑制しています。最適化後は幅警告を抑制せずコンパイルが通ります。
配布版は既存の幅警告が多数あるため `-Wno-fatal` で比較します。

## MAX10リソース評価の限界と実機側の確認

QSFの指定は `10M08SAE144C8GES`。公称8K LE・378 KbitのM9Kを持つ機種です
（[Altera公式ボード仕様](https://docs.altera.com/r/docs/812857/current/max-10-fpga-10m08s-evaluation-kit-user-guide/board-component-blocks)）。
M9Kは9 Kbit単位なので全体で42ブロックです。

**表の数値はアクセラレータ単体のYosysによる推定であり、QuartusのLE使用率や
全NESの収容保証ではありません。** このYosysの `synth_intel` は実験的なバックエンドで、
独立した2書き込みクロックのグリッドRAMは `$mem_v2` のまま残ります。
スクリプトでは残ったRAMが元と同じ2,048×8 bit・同期2read/2writeであることを検査し、
M9K数2は1,024×8構成を2ブロック使う想定として明記しています。
追加M9KやDSPを要求する構造は導入していません。

配布版からはFFが301個、組合せセルが208個増えます。
前回からの差はFFが16個減少、組合せセルが15個増加です。
FFとLUTはLE内で共有される場合があるため、両者の単純和をLE使用数として扱えません。
`resources.py` は組合せセル1,300以下、FF600以下、DSPなし、グリッドRAM形状不変を
今回の単体ガードとしています。これらはデバイス全体の容量判定の代わりにはなりません。

この環境にはQuartusと実機がなく、最終のFitter・TimeQuest・実画面は未検証です。
実機のある環境では、元の `quartus/nes_top_max10.qpf` を開いて再コンパイルし、
全体のLE/レジスタ/M9K/DSP使用率、グリッドのM9K推論、PLL由来10 MHz/100 MHzの
セットアップ・ホールドとクロック間パスを確認してください。制約を緩める変更はしていません。
その後、READMEの6点のハッシュと表示を確認します。
