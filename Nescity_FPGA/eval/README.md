## 結果

2026-09-06、配布版 `a614553` および前回の4行バッファ版 `93d2113` と比較。
前回版は検証済みの基点としてコミット・Push済みで、今回もその後続コミットです。

前回から**2.08倍**、計算時間は約52%減です。M9Kを増やさずに、組合せセル450個・
FF 317個を追加して、1クロックごとに1セルを処理します。
リソース比較の方法を修正し、配布版と前回版も同じ方法で再推定しました。
前回のコミットに記録された組合せセル数と直接差し引かないでください。

CPUクロック100 MHz、計算クロック10 MHzで測定しています。描画、CRC計算、
NES命令によるポーリング等を含む実機全体の速度ではありません。
CPU側の半周期を7 nsに変えた通信試験では1,103～1,104クロックでした。

## 設計

### グリッドの2バンク化

2 KiBのグリッドを、各1,024×8 bitの独立した2個のRAMに分けます。
各バンクのポートAは固定の計算クロック10 MHz、ポートBは固定のCPUクロック100 MHzです。
元世代のバンクから読みながら、同じクロックで新世代のバンクへ書き込めます。
クロックの切り替えやRAMポートの追加はありません。

各バンクの有効セルは0～959。CPUには従来と同じ960セルの窓を見せ、
CPUの読み書きは現在バンクを選択します。BUSY中のCPU書き込み禁止、
START/DONEのトグル同期、完了後のバンク交換、MMIOの仕様を維持します。

### 行バッファと行末での先読み

各列について過去4行を32 bitにまとめ、32ワードの同期RAMに保持します。
世代開始時には元バンクの28・29・0・1行目を128回の読み出しで補充します。
その後は下側の1セルだけをグリッドから読み、行バッファの4セルと合わせて
縦5セルを集計します。初期化は毎世代全ワードを書き直すので、CPUの盤面再ロード、
バンク交換、リセット後にも古い履歴を消費しません。

最初の行は `x = 30,31,0,1,2,...,31,0,1` の順に36列を処理します。
先頭4列の集計を、61 bit×4個のFFキャッシュにも保存します。
末尾で再び必要になる30・31・0・1列は、そのキャッシュから再利用します。
空いた読み出しで次の行の先頭4列を集計し、使い終えたキャッシュの同じ枠に保存します。
行バッファは各列を最初に読んだ時点で進めてよく、末尾の再利用には更新前の集計が残ります。

次の行は、この4列をまとめて窓の左側へロードし、2列目（走査位置4）から処理を続けます。
前の行の最終セルをSUM段へ保存するのと同じクロックで窓を入れ替えるため、
行間の補充待ちがなく、最初の4クロック以外は連続して出力が流れます。
最終行の末尾4列では次行の先読みを行いません。
有効なグリッド読み出しは `128 + 30 × 32 = 1,088` 回／世代です。

5×5の重みは `w = (3 - |dy|) + (2 - |dx|)` と分解します。
5列の集計をFFに保持し、セルを右に移すときは4列を再利用します。
人口15～24の影響力は重みに依存しない `+2` なので、重みを掛ける係数を0にし、
縦方向の集計に一度だけ加えます。通常範囲外の101～255も元実装と同じ扱いです。

### 毎クロック進む演算

同期RAMの読み出しに1クロックのタグ遅延を付け、次の段を重ねて実行します。

| 段 | 処理・保存する内容 |
| --- | --- |
| 列集計 | 縦5セルを集計、または行頭の集計を再利用して窓へ追加 |
| SUM | 5列の人口・影響力・分類個数・自セル・出力位置を保存 |
| AVG | 平均・都市数を計算。他の必要な値と位置も次段へ渡す |
| BIAS | バイアスを計算し、自セル・影響力・平均・位置を保持 |
| NEW_VALUE | 増減量の制限と最終クランプを行い、値と位置を保存 |
| 書き込み | 新世代のバンクへ1セルを書き込む |

各段は別のセルを扱うため、平均計算後の分類個数にも専用のレジスタを持ちます。
最終セルの書き込みを完了した次のクロックでDONEを通知します。
RAM・列キャッシュの内容自体にはリセットを付けず、有効フラグと完全な補充で初期化します。

行バッファでは、前の列の書き込みと次の列の読み出しを同時に行います。
有効データを読むときのアドレスは異なります。補充中の同一アドレス衝突の出力は消費せず、
`no_rw_check` の動作を確認するため、その衝突時の出力をXにするモデルでも検査します。

演算幅は人口の重み付き合計が15 bit（最大16,575）、影響力が符号付き9 bit
（−130～195）、分類個数が5 bitです。`/65` はシフト・減算・1回の余り補正、
`(force−20)/20` は境界比較を使い、Cと同じゼロ方向への丸めを維持します。
過密度の `/3` は符号なし8 bitです。

計算本体は `128 + 1 + (36 + 29 × 32) + 6 = 1,099` クロックです。
内訳は履歴補充128、最後の補充取り込み1、列走査964、読み出しと演算の排出6です。
開始同期と完了通知を含む測定値は1,103クロックになります。

## 再実行

C/C++コンパイラ、Python 3、Verilatorが必要です。追加検査にはIcarus Verilog、
リソース比較にはYosysを使います。合成後ロジックの検査にもIcarusを使います。Python外部パッケージは不要です。
[OSS CAD Suite](https://github.com/YosysHQ/oss-cad-suite-build) の `bin` をPATHに入れてください。
今回のツールは `/tmp/mics-fpga-tools/oss-cad-suite/bin` に配置しました。
リポジトリのルートから実行します。

```sh
export PATH=/tmp/mics-fpga-tools/oss-cad-suite/bin:$PATH

# 本検証：355配置、2,058世代。追加で算術と4値シミュレーションを実行
python3 Nescity_FPGA/eval/run.py --extra-checks

# 元回路の速度・動作を同じMMIOドライバで測る短い比較試験
python3 Nescity_FPGA/eval/run.py --baseline --steps 2 --smoke

# 前回の4行バッファ版も同じドライバで比較
python3 Nescity_FPGA/eval/run.py --rtl-ref 93d2113 --steps 2 --smoke

# CPUクロックとの位相関係を変えた本検証
python3 Nescity_FPGA/eval/run.py --cpu-half 7

# アクセラレータ単体の合成比較とRAM/DSP・論理規模のガード
python3 Nescity_FPGA/eval/resources.py --check-netlist
```

短い動作確認には `run.py --steps 2 --smoke --extra-checks` を使えます。
生成物・ログは `.build/` に保存され、Git管理対象から除外されます。
回路やテストコードを変えたら `results.json` の過去測定とは区別してください。
スクリプトは失敗時に非ゼロで終了します。コンパイル詳細は `.build/*-build.log`、
合成詳細は `.build/*-synth.log` を参照してください。

## 正しさの検証範囲

`reference.c` は変更していないルートの `linux_city.c` を取り込みます。
Pythonから共有ライブラリ経由で初期配置・次世代を生成し、Verilatorで動かす
実RTLにCPUのMMIO経由で書き込み、各世代の全960セルを比較します。
RAMを内部から直接書き換える方式ではありません。

- 標準初期配置の1,280世代と、READMEのCRC全6点：
  `0000:37C2 / 0100:4963 / 0200:D350 / 0300:593A / 0400:EE30 / 0500:1FC3`。
- 0～255の全256種類の一様盤面を2世代ずつ。
- 分類境界の混在、通常値・全バイト値・海や山が多い固定乱数64配置を3世代ずつ。
- 四隅など7地点×4背景の単一セル配置を2世代ずつ、縦横の縞6配置を3世代ずつ。
- 正誤のアンロック列、長い書き込み、レジスタ署名、960セルの窓の範囲、
  BUSY中の読み出し・書き込み・制御命令、DONEの保持、世代カウンタ、
  ソフトリセット、計算中の非同期リセットと再アンロック。
  補充・各演算/読み書きフェーズ・行境界・最終セル付近の33時点でリセットし、
  再初期化後に1世代を正常完了できることも確認。
- `/65` の到達可能な16,576入力と、影響力326入力を全数検査。
  全65,536組のself/avgに固定乱数の分類集計を与えてbias/deltaを元RTLと比較。
  全256 self×5 deltaの最終クランプも比較。
- Icarusの4値シミュレーションで初期化されていないRAM・行バッファ・両方の列キャッシュを含めて
  2世代を実行し、両バンクの全セルにXや誤値が現れないことを確認。
  行バッファの同一アドレス読み書き衝突で出力をXにする評価用モデルでも同じ検査を実行。

4値RTL検査では、各世代のグリッド読み出し1,088回と、0～959番の出力が
欠落・重複・クロックの空きなく連続して書き込まれることも検査します。

`resources.py --check-netlist` は、合成後のLUT/FFと未マップRAMについても
4値シミュレーションで標準配置2世代・両バンクを比較します。

Verilatorの `MULTIDRIVEN` 警告のみ、元からの独立2クロック真のデュアルポートRAMに
対して抑制しています。最適化後は幅警告を抑制せずコンパイルが通ります。
配布版は既存の幅警告が多数あるため `-Wno-fatal` で比較します。

## MAX10リソース評価の限界と実機側の確認

QSFの指定は `10M08SAE144C8GES`。公称8K LE・378 KbitのM9Kを持つ機種です
（[Altera公式ボード仕様](https://docs.altera.com/r/docs/812857/current/max-10-fpga-10m08s-evaluation-kit-user-guide/board-component-blocks)）。
M9Kは9 Kbit単位なので全体で42ブロックです。

**表の数値はアクセラレータ単体のYosysによる推定であり、QuartusのLE使用率や
全NESの収容保証ではありません。** RAMはすべて `$mem_v2` として残し、
形状・読み書きポート数・同期クロックを検査します。現在の構成は、
1,024×8 bitの独立2クロック・2read/2writeのグリッド2個と、
32×32 bitの単一クロック・1read/1writeの行バッファ1個です。
行頭の集計キャッシュは4枠を同時に読むためFFになり、M9Kは増えません。

グリッドは各1 M9K、行バッファは256×32構成の1 M9Kに収まる想定です。
MAX10の単純デュアルポートは256×32構成を扱えます
（[Altera公式メモリ構成表](https://docs.altera.com/r/docs/683431/current/max-10-embedded-memory-user-guide/memory-configurations-for-dual-port-modes)）。
M9K数は容量・ポート構成からの推定で、物理マッピングの成功を意味しません。

### 評価ツールの制限への対処

この版の実験的な `synth_intel` に付属する `intel/common/brams_map_m9k.v` は、
独立した読み書きポートを受け取っても、読み出し側の `A1ADDR` を接続せず、
書き込み側の `B1ADDR` だけで `SINGLE_PORT` の `altsyncram` を生成します。
この変換を正しいRAM実装として使えないため、`resources.py` ではBRAM変換を通さず、
`ramstyle` 属性のあるメモリをFF化からも除外してからLUT/FFを合成します。
前回の「交互のアクセスが単一ポートへ最適化された」という説明は撤回します。
RTL自体の検証結果は変わりませんが、論理規模は今回の方法で全版を再推定しています。

また、付属の `intel/max10/cells_sim.v` の `dffeas` モデルはイネーブルを無視し、
非同期クリアも必要な動作をしません。合成後の論理検査では `mapped_cells_sim.v` を使い、
有効な4入力LUTモードと、アクティブLowクリア・イネーブル付きFFモードだけを検査します。
スクリプトが各セルのパラメータと未使用制御端子を確認し、対応外のモードは拒否します。
これは論理機能の評価モデルであり、Altera製のタイミングモデルではありません。

単体のガードは組合せセル2,000以下、FF900以下、DSPなし、グリッドの合計16,384 bit、
上記のRAM形状だけであることです。行頭4列の集計244 bitと各パイプライン段の保持分を
許容して前回の上限から更新しました。今回の増分は450組合せセル・317 FFです。
FFとLUTはLE内で共有される場合があるため、両者の単純和をLE使用数として扱えません。

### 全体のM9K使用見込み

有効な `CITY_ACCELERATOR` 構成のソースから主要なメモリを積み上げると次の通りです。
未使用の通常ROM構成や、QIPに登録されているだけの未インスタンスIPは含めません。

| メモリ | 論理容量 | 想定M9K |
| --- | ---: | ---: |
| `cart.v` のPRG | 16 KiB | 16 |
| `cart.v` のCHR | 8 KiB | 8 |
| `cart.v` の独立WRAM | 8 KiB | 8 |
| `wram.v` | 2 KiB | 2 |
| `vram.v` | 2 KiB | 2 |
| `ppu_spr.v` のOAM | 256 × 8 / 64 × 32 | 1 |
| アクセラレータのグリッド | 2 KiB | 2 |
| 行バッファ | 32 × 32 bit | 1 |
| **主要メモリ合計** | | **40 / 42** |

残る2ブロックは余裕が小さいため、全体で空いていると断定できません。
パレットROM（64×15 bit）や小さいPPU配列などをQuartusがRAMへ割り当てるか、
実際のポート構成で何ブロックに分割するかをFitterで確認する必要があります。
この表はソースからの容量見積もりで、全体合成の測定値ではありません。

この環境にはQuartusと実機がなく、最終のFitter・TimeQuest・実画面は未検証です。
実機のある環境では、元の `quartus/nes_top_max10.qpf` を開いて再コンパイルし、
全体のLE/レジスタ/M9K/DSP使用率、グリッドと行バッファのM9K推論、
PLL由来10 MHz/100 MHzのセットアップ・ホールドとクロック間パスを確認してください。
特にBIAS段とDELTA＋クランプ段の10 MHzタイミングを確認します。
制約を緩める変更はしていません。その後、READMEの6点のハッシュと表示を確認します。
