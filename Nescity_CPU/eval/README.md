# Nescity CPU 高速化と実機なしの評価

> 公開用リポジトリについて：編集対象とevalだけを収録しています。下記の旧コミットID・`baseline`タグは元の非公開評価環境の記録で、このリポジトリには存在しません。比較評価には配布物と元の評価履歴を手元で用意してください。再実行する場合は、元の非公開リポジトリの対象部門ブランチから別のローカル作業ツリーを作り、この部門の実装とevalをコピーして使います。

既存の配布ファイルで編集したのは `Nescity_CPU/8bitworkshop/nescity.c` だけです。
この `eval/` はローカルでのビルド・評価・変更説明用に追加しました。

## 編集範囲とGit

配布元の `README.txt` は、CPU部門を「6502のプログラムを修正することで高速化」と
説明しています。`Nescity_CPU/README.txt` には、さらに狭いファイル単位の編集制限は
ありません。一方、`Nescity_FPGA/README.txt` の「cart/city_accelerator_nowater.v
だけをいじって良い」は論理回路部門の指定です。今回はCPU部門として扱いました。
同梱資料以外の大会規則は確認対象に含めていません。

全配布物を最初のコミットと `baseline` タグに保存しています。
前回の高速化版は `07b8126` に保存済みで、今回の評価でも再ビルドして比較します。
FPGA側、配布済み `.sof` / `.nes`、描画・CRC・CHRのアセンブリ、`linux_city.c` は
元の内容を保持しています。

```sh
git log --oneline --decorate
git diff baseline -- Nescity_CPU/8bitworkshop/nescity.c
git diff 07b8126 -- Nescity_CPU/8bitworkshop/nescity.c
git diff --stat baseline
```

## 高速化の内容

- 5行の旧世代参照先を行ごとに決め、25近傍それぞれの座標変換を削減。
  行アドレスのROM表を使い、下端では従来どおり `top_rows` を参照します。
- 5列分・74バイトの集計を循環バッファに保存。重みを `3-|dy|` と `2-|dx|` に
  分け、縦集計の和に中央3列の `1,2,1` 倍を加えると元の5×5集計になります。
  先頭3列の人口和・影響力を9バイトで複製し、左右の参照を固定オフセットにします。
  右に進む際に1列だけを交換します。草原の影響力は重みに関係なく `2` なので、
  横方向の加算係数を0にします。
  集計は行をまたいで保持し、世代の開始時だけ初期化します。5列すべてを入れ替えると
  旧集計が完全に差し引かれるため、途中に海だけの行があっても新しい窓は正確です。
- 影響力に重み1あたり2を加えて、列の集計を符号なし8ビットで処理。
  全近傍で加わる130は最終変換表で相殺します。人口和は16ビットを保持し、
  下位・上位バイトを別配列にして、配列アクセスの添字計算を減らします。
- 海・山・山以外の自然・住宅・商店・高層を独立した8ビットカウンタで数えます。
  山は自然の個数にも含まれる元の規則を、最後の加算で再現します。
  入れ替える列で同じ個数の分類は、窓のカウンタ更新を省略します。
- 縦5セルが同じ値なら、小さなROM表で集計を直接取得します。さらに、取り除く
  列も同じ一様列なら、窓全体の集計は変わらないため更新を省略します。
  この判定はすべての値 `0..100` に対応し、世代の開始時にキャッシュを無効化します。
- 重み付き人口和の `/65` は、全入力 `0..6500` の正確な商を格納した6501バイトの
  ROM表に置換。`/20` は326バイト、過密度の `/3` と4倍は101バイトの表で
  置換し、負数の除算も従来のゼロ方向への丸めを保持します。
- 列の集計、セルの更新、行ループを `nescity.c` 内の6502インラインアセンブリで
  記述し、Cの汎用補助関数呼び出しや不要な16ビット演算を削減。
  通常の6502命令だけを使い、各ブロックでcc65の最適化を無効にして
  キャリーとレジスタの寿命を明示しています。
- 平均人口の補正は最大でも `+1`、過密度補正は必ず非正です。したがって平均を
  調べる前に差分が `-4` 以下なら最終差分は必ず `-3`、値1で差分が負なら最終値は
  必ず1です。住宅が2未満の山は、影響力を集計する前に値1と確定できます。
  海が4以上なら差分は平均補正前でも最大 `7-4-3-2=-2`、海が3以下なら
  影響力の上限126から最大 `5-4-3=-2` となるためです。
  これらの場合だけ平均計算を省略します。初期配置やステップ数の決め打ちはありません。
- 32列それぞれについて縦5セルの住宅数を36バイト（端の複製4バイトを含む）で保持。
  次の行へ進む前に、抜ける旧行を引き、入る旧行を足します。書き戻しより前に更新し、
  下端では保存した先頭2行を使います。海だけの出力行でも住宅数は更新します。
- 海と、住宅が2未満の山では出力を確定し、重い列集計の更新も先送りします。
  次の計算対象までの距離を1バイトで保持し、距離が5未満なら重なる列を再利用、
  5以上なら5列を入れ替えます。初期配置・世代数に依存せず、住宅数から判定します。
- 世代ループもインライン6502命令で実行。次世代3行のポインタをROM表から取り出し、
  汎用C引数の受け渡しや配列アドレス計算を減らします。世代更新内の行コピーは32バイト
  専用で、8バイトずつ展開します。旧先頭2行の保存、2行遅れの書き戻し、最後の2行の
  書き戻しは元の順序を維持します。海だけの行は集計せずに出力します。
- 横位置をYレジスタに保持し、固定セルではRAMの位置カウンタを書き換えません。
  計算対象に着いた時だけ前回位置との差を求め、必要な列集計を追いつかせます。
- 列の人口和の上位バイトをXレジスタに保持し、下位バイトの加算で実際に繰り上がった
  場合だけ増やします。値0～100、対称2セルの和が最大200であることを使い、
  不要な16ビット値の読出し・書込みを削減します。
- 計算用変数はリンカ管理のゼロページに配置。通常RAMのCスタックに余裕を
  残します。ROM表をRAMにコピーせず、32 KiBのPRG枠に収めています。

セル値の有効範囲は元の規則と同じ `0..100`、重み付き人口和は最大6500、
影響力の和は `-130..195` です。水不足値が大きい場合の8ビット減算は、
結果が確実に最大衰退になる範囲で飽和させます。
成長・衰退・水不足の適用式、3行のローリング書き戻し、初期配置、CRC、
世代カウンタ、6フレームの待ちと再描画頻度を保持しています。
水不足の自動計算は配布版同様に無効です。
世代更新の主要15関数に汎用の乗算・除算・剰余ルーチン呼び出しがないことを、
生成アセンブリで検査します。初期化や数字描画の乗除算は計算速度の測定範囲外です。

## 再現手順

必要なのは Python 3、Git、make、ホストのCコンパイラ (`cc`) です。
初回のみGitHubへの通信が必要です。システムへのパッケージ導入は行わず、
依存ツールを `.tools/` に固定コミットで取得してビルドします。

```sh
# リポジトリのルートで実行
python3 Nescity_CPU/eval/bootstrap.py
python3 Nescity_CPU/eval/verify.py

# 短縮評価：5世代 + 223配置 + 除算置換の全入力
python3 Nescity_CPU/eval/verify.py --quick

# ROMのビルドのみ
python3 Nescity_CPU/eval/build.py

# verify.pyでビルドしたROMの関数別サイクル内訳
python3 Nescity_CPU/eval/profile.py
python3 Nescity_CPU/eval/profile.py --variant previous --steps 5
```

`bootstrap.py` が依存の取得・ビルドに失敗した場合は終了します。
ビルドログは `build/toolchain-build.log` にあります。
取得するコミットはスクリプトの `PINS` を参照してください。

ビルドは3版とも `-t nes -Oirs -Cl -g` を使い、8bitworkshopの `neslib2.cfg`、
`crt0.o`、`neslib2.lib` をリンクします。ブラウザのコンパイラそのものではないため、
配布ROMとのバイナリ一致は保証しません。評価は同じ固定ツールチェーンで
再ビルドした配布版・前回版・今回版を比較します。

依存ランタイムの古い `sp` 名に対する非推奨警告と、macOSリンカがホスト評価用
配列のアラインメントを縮小する警告は、この固定依存で確認済みです。

## 出力と使用方法

- `build/optimized/nescity.nes`：高速化版ROM。CPU部門の `MICS2026_CPU.sof` 用。
- `build/baseline/nescity.nes`：変更前ソースを同じ条件でビルドした比較用ROM。
- `build/previous/nescity.nes`：前回の高速化版 (`07b8126`) の比較用ROM。
- 各ディレクトリの `nescity.map` / `nescity.lbl` / `nescity_generated.s`：
  メモリ配置・シンボル・生成6502コード。
- `build/results.json`：サイクル数、資源量、スタック余裕、検証結果。
- `build/{baseline,previous,optimized}/*.bin`：各世代の全960セルを連結した検証用データ。
  `.log` には実行サイクルとCRCを保存します。
- 各版の `profile.csv` / `profile.json` / `profile.log`：`profile.py` 実行時に生成。
  命令アドレス別・関数別のサイクル数。関数別の値には呼び出し先を含めません。
- `build/optimized/math.log`：全6501入力の平均計算と、除算置換表の全要素の検証。

生成物と依存ツールはGitの対象外です。計測済みの概要は [RESULTS.md](RESULTS.md) にあります。
8bitworkshopには、従来のプロジェクトの `nescity.c` を更新して使用できます。
実機が利用できる際は、CPU部門READMEの手順で `.sof` を設定し、上記の高速化版ROMを
`romwriter` で読み込んでください。

## 何を検証するか

`rom_runner.c` は [cc65 sim65](https://cc65.github.io/doc/sim65.html) の6502コアを
変更せずに組み込みます。完成したNES ROMのPRG領域を本来の `$8000` に配置し、
リンカのシンボルから初期化・世代更新・CRC関数を実行します。
通常RAMを2KBに制限し、カートリッジRAMを使う抜け道を設けていません。
比較対象は [同梱Linuxモデル](../../linux_city.c) をそのままインクルードした
`reference.c` です。

標準の `verify.py` は次を確認します。

- 初期状態から1280世代まで、3版のROMとLinuxモデルの全セルを毎世代比較。
- 実ROMの平均計算関数を入力0～6500すべてで実行し、ホスト側の `/65` と照合。
  実ROMに入った符号付き除算表326要素と過密度表101要素も全数検査。
- CPU READMEの0～5世代と、FPGA READMEの256～1280世代の既知CRCに一致。
  実ROMのCRCアセンブリもPythonの独立したCRC実装と比較。
- 0～100すべての一様配置、分類境界の混在、四隅と上下左右の回り込み、
  海の連続区間、陸が1セルだけの配置、固定乱数32配置をそれぞれ2世代評価。
  海や山が多い乱数32配置と、列キャッシュの再利用・無効化を試す縦縞4配置を追加。
  さらに住宅0/1/2件と海0/1/3/4/12/22セルの組み合わせ18配置で、山の早期判定と
  その適用境界を独立した元のモデルに照合します。
  計算対象セルの間隔0～31を海・山の2種類で試す64配置と、海だけの行を挟む
  4配置も検証します。人口和の255/256・767/768などの繰り上がり境界を含む
  非一様な縦5セルと周期境界を組み合わせた20配置も追加しています。
  合計279配置で、水不足値 `0/1/12/127/128/129/134/135/254/255` も検証。
- リセットベクタから通常のmainを実行する起動試験。周期的なNMI、CRC更新、
  5回の再描画を経て、盤面とネームテーブルが一致することを確認。
- ROM容量、ゼロページ、通常RAMの配置、Cスタックと静的データの衝突、
  ハードウェアスタックの使用域を検査。意図的な衝突設定が失敗することも確認。
- 既存アプリケーションの変更範囲が `nescity.c` のみであることを確認。

## 評価の限界

計算サイクルの測定はNMI・描画・待ち時間を除いた `sim_step` の実ROM命令です。
起動試験のPPUは簡易モデルで、VBlankフラグ・VRAM書き込み・周期NMI・DMAの
待ちを模擬します。画像を描画する完全なNESエミュレータではなく、その総サイクルを
実機のフレームレートとしては扱えません。FPGA実機、Quartusによる合成、
タイミング収束、実機上の表示・処理速度は未検証です。

CPU部門の回路と `.sof` を変更していないため、追加のLE・FF・BRAMは要求しません。
FPGAの使用率そのものは再計測できていません。ソフトウェアのRAM・ROM容量と
スタック余裕を今回の資源評価としています。
